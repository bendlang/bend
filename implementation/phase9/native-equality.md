# Guarded native equality for the current checked compiler

The maintained equality derivative now recognizes the current b2111cf-generated
compiler as a separate reviewed profile. It inserts one guarded JavaScript string
comparison into `String.eq`; all other generated bytes remain unchanged. The
candidate is an explicit derivative of a genuine checked B1, not a new bootstrap
or self-hosted fixed point. It has not been installed by this experiment.

The frozen [P9-001 plan](../../experiments/phase9/P9-001-native-equality.md) states
the hypothesis and gates. Root's Phase9 timing report owns any controlled
full-source speed conclusion; the controls below are not a speed benchmark.

The subsequent [P9-006 guard investigation](current-equality-guard.md) adds a
version-3 default for the current emitter after broader UTF-16 proof and controls.
The version-2 candidate and evidence described here remain exactly replayable;
historical version 1 also remains unchanged.

## Implementation and semantic boundary

The old pin retains its original runtime/body/upstream/recipe hashes, replacement
bytes and version-1 transformation statistics. The new pin has a separate
version-2 profile: argument names and direct calls changed, `run_jump` disappeared,
and public compiler exports now contain explicit identity-marshalling wrappers.
The new export parser accepts their exact reviewed syntax, including the genuine
zero-argument ABI-query root. An unknown wrapper shape is refused.

For two well-formed primitive strings, the added guard returns host equality.
Malformed UTF-16 and non-string values execute the unchanged helper. This matters
because the new upstream helper no longer validates each compared character via
`char_new`; its malformed-string observations differ from the old pin. Each
profile is tested against its own original artifact. The claim assumes standard,
unmodified JavaScript built-ins and does not promise equivalent resource-exhaustion
behavior or arbitrary monkeypatched/proxy-host behavior.

Derivation still requires the genuine bootstrap/API/Base/source/module and recipe
identities. It additionally binds the recognized emitter profile to the bootstrap
revision. Replaying old releases uses the unchanged version-1 result. Duplicate,
nested, shadowed and rebound protected names, altered helper bodies/runtime,
changed public wrappers and changed provenance are rejected by the maintained
guards.

## Final boundary and historical compatibility gates

`equality-controls-05` completes **12/12 groups** on the current API and 12/12
registered groups on the old API. The old pin has **11 applicable groups**; the
current-export wrapper case is explicitly recorded as inapplicable there.
Named reports retain Unicode/astral/combining/NUL and malformed UTF-16 pairs,
non-string/fallback demand, staged arguments, extra arguments, exact single
insertion, adversarial syntax/binding/provenance refusals, and actual public
compiler calls. The public API control exercises a zero-argument ABI query,
curried path concatenation, ignored extra arguments and checker input immutability.

`equality-legacy-release-01` additionally verifies the authentic preserved old
release package with the new maintained helper and reproduces its installed
API bytes exactly with version-1 transformation statistics. This is a read-only
historical compatibility gate; no default installation occurs.

## Actual compiler controls

`equality-compiler-02` passes all **27 paired cases**: 24 checks and three emitted
JavaScript programs. Verdict, phase, checked/type-accepted state, trust result,
diagnostic and output observations agree exactly. All three generated JavaScript
files are byte-identical and their executions match the upstream fixture output:
`closures_hof`, `beta_nested_redex` and `string_algorithms`.

The checking cases include the 21 maintained declaration/import controls plus
alpha equivalence, a rejected annotation and rejected binder-name capture.
The two variants use the immutable release07 host/runtime and separately validated
Base caches. The harness records exact inputs and rechecks them after execution.
Its timings include cache/setup work and overlapped other authorized work; they
are not evidence of a whole-checker speedup.

Maintained reproduction helpers are
`selfhost/tools/performance/phase9/equality-controls.mjs`, `equality-worker.mjs`
and `equality-legacy.mjs`. Raw requests, generated code, actual program outputs,
worker copies and result reports remain under `selfhost/build/phase9/` pending
final phase preservation.

## Retained setup failures

- `equality-controls-01` refused the actual zero-arity public ABI export. The
  bounded wrapper grammar was corrected to include arity zero; no unchecked
  permissive fallback was added.
- `equality-controls-02` records both successful test processes; explicit named
  test-group JSON was added in controls-03 for clearer evidence accounting.
- `equality-compiler-01` wrongly assigned a positive oracle to upstream
  `beta_ann_body`, which intentionally rejects a mismatched annotation. Its
  source, request and failure are preserved. Correcting that oracle produces
  controls-02; the compiler was unchanged.
- `equality-controls-04` assigned a high-level path-join expectation to the
  low-level `f_path_join` API, which concatenates an already separated prefix.
  The actual observation is retained in `public-diagnostic.json`; controls-05
  supplies `folder/` and additionally captures named failure details.

Root independently reviewed the dual profiles, runtime/body guards, exact export
marshalling, fallback behavior, bootstrap revision binding and exact replay. No
blocking issue was found. Selected controls establish a bounded implementation
candidate accepted for integration. The first combined `integrated-01` workflow
uses the equality profile, completes its genuine bootstrap, and passes all 21
maintained controls while retaining 12 exact TypeScript observation differences.
It also contains separate checker source changes, so those results do not isolate
the equality derivative's contribution. Broad conformance, controlled timing and
installed-release acceptance remain separate root-owned decisions. No isolated
whole-checker speedup is established by this experiment.
