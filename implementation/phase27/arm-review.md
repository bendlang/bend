# Phase27: independent selected-arm review and compiler component

**Source-review result: no blocking semantic defect found in the inspected rule.** This review covers the narrowly guarded constructor-arm prebinding implementation, not general arity raising or a whole-emitter correctness theorem. Execution evidence belongs to the root-owned checked build, paired controls and uninstrumented timing campaign. The reviewer did not write `arm.bend` or change compiler/runtime source.

## Recognizer and generated behavior

[arm.bend](../../selfhost/src/back/js/arm.bend) is reached only through `j_match`'s existing single-remaining-constructor path. It requires a live function input, a literal leading-lambda arm, a real datatype owner and constructor, and an input refinement that has not removed that constructor. Specialization must produce a complete live-field telescope ending in that owner. Zero-field, erased-field and unrecognized telescopes retain `matcher1`.

The arm walk checks function types through every leading lambda and rejects lifted factories. It follows annotations and dependent output substitution in the same way as `j_lambda_code`. The total lambda count must exceed the constructor-field count: the intended result is a partial arm, not an already computed body. Remaining erased parameters retain the existing null ABI slot and delayed evaluation rules through `j_lambda_code`; rejecting erased constructor fields avoids inventing a new projected-field layout.

The replacement keeps the outer `fn(1,...)` entry. It calls the same `project`, reads `p.length` once, and uses the original generic jump/arm behavior when the observed count differs. This preserves trusted foreign record projection rather than adding a tag test. The ordinary path keeps `p.slice()` and returns a function with the original total arity, `env:null`, and the copied field vector as `bound`. The next source argument still arrives through the existing application path. No subsequent argument expression moves before a match or an earlier error.

The selected arm's `function(a){...}` body is still generated by `j_lambda_code`. The `(0,function(a){...})` expression deliberately avoids inferred name `c`, retaining the ordinary anonymous code-function name. Lexical captures, anonymous function identity per invocation and explicit argument binding remain local to the match. Deep recursion and constructor effects still return the same `jump`/`build` work to the runtime; this change does not replace the trampoline or eagerly construct nested values.

## Important non-obvious cases

A field vector's original length does not guarantee its `slice()` result has that length. Trusted foreign objects may supply a custom method or proxy. The implementation therefore copies all of `apply`'s **post-slice** branching, not only its expected partial case: exact copied arity calls the code; short copied arity returns a partial; overapplication slices the prefix, calls the code, forces that result before obtaining the final suffix, and returns the same jump. The order and number of copied-vector `length` reads match the inspected runtime. This addresses the concrete counterexample where a nominal two-field projection's slice returns enough fields to execute the arm immediately.

The original field snapshot's left-to-right getter observations remain because `slice()` is retained. Binding the fields as captured locals in a new smaller-arity closure would have changed partial descriptors and could have changed field-read timing; this implementation avoids that alternative. Eta-short arms cannot qualify because their explicit lambda count does not exceed the whole constructor-field count. Missing/malformed fields use the generic path, and function-valued bodies/overapplication remain governed by the runtime-equivalent sequence.

The remaining maintenance cost is real: a short piece of `apply` now exists both in the runtime and in generated-string construction. Any future runtime change to post-slice length tests, receiver, force order or suffix slicing must update this lowering and its semantic controls together. Counters alone cannot catch such drift. Custom-slice/proxy traces, early-error versus later-argument demand, returned descriptors and deep successful output are the meaningful controls.

## Complexity and promotion cost

The candidate adds62 physical/54 nonblank Bend lines, eight definitions and3,665 source bytes. It introduces one selected-arm prebinding rule; the main conceptual cost is duplicating the post-slice application schedule in emitted strings. It is a performance specialization, not a reduction in source concepts or lines.

For the aligned real component, `has_name`'s registration grows289→567bytes (+96.2%); the complete emitted module grows66,641→66,919bytes (+0.42%). The fixed overhead can therefore be substantial for an individual small function even when modest for the library. Broader generated-image size and compiler emission cost remain separate measurements. A demonstrated runtime gain on the actual helper plus unchanged demand/ABI controls is the appropriate justification; saving an instrumented dispatch count alone would not justify promotion.

## Independent longer-warm harness review and decision boundary

Read-only inspection of `phase27/measure-warm.py`, its recorded `timing-warm-01.launcher.py`/receipt, point configuration and the maintained `execute.mjs` found no blocking comparison change. The recorded transformation preserves original input hashes, expected-result checks, serial CPU3 execution, fresh child processes, five samples per side and rotating three-variant order. It changes the calibration target from150 to500ms and uses the explicit common warmup floor of200 calls **and**500ms. That conjunction is enforced by the execution runner's loop, and applies independently to old, candidate and upstream.

The measurement duration is a **500ms calibration target**, not an enforced500ms minimum: the calibration runner stops a doubling trial after at least50ms (or its cap), then extrapolates repetitions, still capped at1M. Actual sample durations must be reported from the results. The configuration extends the prospective screen to the real membership component and Boolean worker as well as the regressing term point; the same policy applies to all three. No source/output changes are mixed into this screen.

Promotion must retain both startup boundaries. A clean longer-warm improvement can establish a useful steady-execution capability, but it does not erase the original20.08% regression on short fresh processes. If longer-warm gains are marginal or unstable, the62-line/duplicated-runtime cost is weakly justified. If gains are clear on relevant workloads and the correctness gates pass, promotion can be considered with an explicit startup tradeoff and without a whole-compiler speed claim. A claim that this candidate improves all execution regimes would remain false. Long-lived self-emitted compiler execution and seconds-scale fresh validation processes may weight these regimes differently; neither was directly timed as a full compiler here.

The completed longer-warm screen contains45 healthy samples, all satisfying both warmup floors. Independent readback recomputed the per-call medians: term2,431.12→2,405.26µs (1.011×; overlapping sample ranges), actual membership644.88→569.71µs (1.132×), and Boolean worker2,077.89→2,003.52µs (1.037×). Sample block durations span400.27–529.61ms, confirming that500ms was a target rather than a floor. Source: `timing-warm-01/report.json`, SHA256 `86271baaff473785ce79a3a2a38fafa2b59c41922be327bbb8ac478f2b5ea357`.

These results support a warmup-sensitive term effect and a clearer long-warm real-helper gain; the term's1.1% median difference is not a convincing independent speedup. They do not correct the original tight five-sample short-window regression. The lead therefore retains this inline variant as unpromoted and tests a separately designed shared runtime helper, with both protocols preserved. This respects the original design's regression gate rather than silently substituting a more favorable warmup policy.

## Second variant: shared runtime callback

The separately designed shared variant changes code shape while preserving the recognizer above. The original inline source, attempt01, emissions, short-window135 samples and longer-warm45 samples remain distinct evidence. This section is a source/bundle review of attempt02, before its performance result; it is not an amendment declaring attempt01 successful.

The emitter now produces `matcher1p(name,count,arity,()=>anonymousCode)`. The shared helper in `selfhost/src/runtime/js/core.mjs` performs the same `project`, single original-vector length read, mismatch fallback, one slice and three post-slice application branches. The code factory runs after projection/length and only creates the existing anonymous function; the eligibility guard prevents a lifted/effectful factory expression. The `(0,function(a){...})` expression still preserves the code name. Captures remain lexical, selected branch bodies remain delayed, and returned partial descriptors still have the original total arity, null environment and copied bound vector. No new semantic blocker was found from moving this schedule into a shared function.

This restores a code-factory call boundary similar to `matcher1` while avoiding its intermediate function record. Sharing the outer callback can plausibly affect V8 compilation/dispatch behavior, but that remains the prospective performance hypothesis. The newly shared callback also captures count/arity/factory metadata; source inspection does not prove a gain. Both original protocols must be rerun before a promotion decision.

The runtime is bundled correctly.
